从 6.2 起，正式发行与维护仅面向 Windows x64，版本、标签和下载文件名遵守下述统一公开版本规则；macOS 构建能力不构成发行承诺。本机未公开测试版不另算发行。更早版本的多平台发行记录仅作历史回执。
当前规则（自 2.0 起）：所有面向用户的版本、GitHub 标签、发行标题及下载文件名只使用两段版本，例如 `2.0`、`2.1`，不发布第三段补丁版本。版本按整数段比较，不按小数或字符串排序；按“逢 9 进 1”，3.9 的下一版为 4.0，再下一版为 4.1。electron-builder 和更新器要求 SemVer，因此仅机器读取的包配置保留末尾 `.0`（6.8 内部版本为 `6.8.0`）；这是同一版本的内部格式，不是另一个公开版本。平台构建号独立递增。版本比较及公开命名回归：`node scripts/check-release-version.cjs`，包含 6.7 → 6.8 与公开／内部相等版本场景。

历史版本曾使用每次增加 0.1 及下列指定例外；后续以以上整数段顺序为准。

1.71 为用户明确指定的例外：从 1.7 增加 0.01，三段配置使用 `1.71.0`。

1.72 同样按本次明确要求增加 0.01，三段配置使用 `1.72.0`。

1.74 按本次明确要求从公开 1.73 增加 0.01，三段配置使用 `1.74.0`。

1.75 的三段配置为 `1.75.0`，GitHub 标签为 `v1.75`。

历史正式版 1.80，三段配置为 `1.80.0`，GitHub 标签为 `v1.80`；它严格高于 1.75。

Windows 工作流只上传 Actions 候选资产，不创建 Release、不改 latest。普通用户发行资产为 NSIS Windows x64 安装 EXE，另附 `latest.yml` 更新元数据；不发布便携包、ZIP、blockmap 或 hash 清单。`latest.yml` 必须随每个 Release 发布：v6.2–v6.6 安装版内置 electron-updater，下载更新前会先取该通道文件来获得文件名、大小与 SHA512，缺失时旧客户端点「下载更新」会直接得到 `ERR_UPDATER_CHANNEL_FILE_NOT_FOUND`。该文件由 `scripts/write-latest-yml.cjs` 从最终安装包字节生成，发布流水线在公开前校验其版本、文件名、大小与 SHA512 与实际安装包一致。GitHub 自动生成的 Source code 快照属于平台系统产物，保留但不列作普通用户发行资产。

许可证履行与普通用户下载资产分开处理：Windows 安装器捆绑以 GPLv3-or-later 构建的 FFmpeg 9.0.2 与 GPLv2-or-later 的 x264，完整对应源码及准确构建脚本必须可通过稳定、无需登录的公开链接获得。候选构建会将 `ffmpeg-9.0.2-x264-b35605a-win-x64-corresponding-source.tar.gz` 放入安装目录根部，作为一个许可证文档随安装器分发；它不是下载页上的另一个安装选项。候选 EXE 与其中对应源码须绑定并验明内容与安装媒体二进制相符。

Windows 当前未配置代码签名证书；EXE 必须明确标为未签名。Windows CI 虚拟机验证不等于用户实体电脑、GPU/HEVC 或长期稳定性验收。
macOS 构建不属于当前或未来发行范围，不需要为同一版本补齐 Mac 资产。

## 真实播放验收

从 2.7 起，进行播放验收时，在隔离测试资料目录中随机选择一部可正常下载的短剧，下载其中两集。每集实际播放约 10 秒，到时先暂停再记录结果，避免工具往返拖长播放。只顺带核对本次改动涉及的播放、快进／回退、控件隐藏或切集，不默认扩大成长时播放或完整矩阵；长时专项需用户明确授权。分别记录音轨解码与人工听音，不能互相替代。

不再依赖旧固定路径素材。下载或播放受阻时记录具体原因与待验项，不得写成通过；离线控件检查和 CI 冒烟不能替代这次真实播放验收。测试资料和视频不纳入公开源码或发行资产。

## Windows 构建

Windows x64、Node 22.12+ 按项目构建配置生成 NSIS 安装程序；正式发布的普通用户下载资产只上传安装 EXE。构建或本地验证不得把便携包、普通源码 ZIP、`latest.yml`、blockmap、hash 清单加入 Release。若当前候选继续捆绑 GPL FFmpeg/x264，对应源码归档应放入安装目录作为随安装程序分发的许可证文档，同时校验源码、构建脚本与内置媒体二进制版本绑定。旧版本构建与媒体工具源码记录不作为新候选版本号或新发布资产数量的例外。
Windows 当前未配置代码签名证书，安装 EXE 必须明确标为未签名。

- README 的版本更新说明须同步新增本版功能摘要，并按新到旧排列；下载区、最新发行链接与更新说明三处一起核对，不得只更新下载版本号。历史版本说明保留。当前正式版为 6.8。
- 历史 4.0 已正式发布，机器版本 `4.0.0`；其安装包、更新清单、源码包与发行标签绑定该版冻结源码。4.0 的三个 artifact 模板使用公开 4.0；依赖版本和旧版资产保留。后续文档提交不改变已发布包与标签。
- 历史正式版 4.4，机器配置 `4.4.0`，latest 为 `v4.4`。三个 artifact 模板使用公开 4.4，发行包、更新清单和源码绑定冻结提交 `23860cfde09d953a7b1f1cbe9e20b433dd4b0e18`；发布后的文档提交不改变包和标签。见 [4.4说明](release-4.4.md)。
- 用户要求 GitHub 根目录每个文件和文件夹的最近提交说明均带当前版本号。发布前从 `git ls-files` 提取第一级路径，包含隐藏根项；根文件须有实际变更，根目录须至少有一个受跟踪子文件实际变更，并进入带本轮公开版本的正常发行提交（4.2 对应 `release: 4.2 统一发行与验证`）。提交后逐项执行 `git log -1 --format=%s -- <根项>`，确认每项最近提交标题含本轮公开版本；只在文件内容写版本、只提交 README 或空提交均不能满足其他根项。推送后由主控核对 GitHub 根目录实际显示并截图，本地结果不能代替远端显示。本轮仅更新有版本标识或发行说明链接的根项目录说明/注释，保留 LICENSE 和批处理文件执行逻辑不变，不为此改动无关业务源码。
- 保留历史版本说明、历史标签、依赖版本和第三方许可正文，不为页面显示改写历史提交。LICENSE 保持标准许可正文，仅允许不影响条文的排版空白调整；批处理文件保持原编码、换行与执行逻辑，代码标识只用注释，禁止改变 CSP 或运行行为来制造提交。

- `LICENSE` 保持可被 GitHub 识别的标准许可正文，不添加版本前言。通过含当前版本的正常提交更新显示；必要时仅调整不影响条文的排版空白，许可条文不变。
